# 环境变量与敏感信息管理

> 目标：**仓库里不再出现任何口令/密钥**，真实值只留在各环境本地的 `.env` 里。
> 涉及范围：jeecg 单体版后端的 4 个 profile（`application-dev / -test / -prod / -dm8`）
> 与集成测试的 `LandTestConfig`。

---

## 1. 一句话用法

```powershell
# 首次：从模板生成 .env，填入真实口令
Copy-Item .env.example .env
notepad .env
```

**之后就能直接启动了，不需要任何额外脚本**：

```powershell
# IDE 里直接 Run 主类   —— 可以
# java -jar ...        —— 可以
# mvn spring-boot:run  —— 可以
```

`.env` 会在启动最早期被 `DotEnvEnvironmentPostProcessor` 自动读成一个
最低优先级的 PropertySource，于是 yml 里的 `${TJ_XXX}` 都能解析。

```powershell
# 跑集成测试（LandTestConfig 自己也会读 .env）
mvn -pl jeecg-module-land test -Pit
```

`.env` 已被 `.gitignore` 忽略，只提交 `.env.example`。

> **为什么不能只靠脚本**：一开始只提供了 `scripts/run-with-env.ps1`，
> 结果 IDE 里点 Run 直接报
> `Could not resolve placeholder 'TJ_DB_HOST' in value "${TJ_DB_HOST}"` ——
> Spring Boot **不认识 .env**，只解析系统属性、环境变量和 `application-*.yml`。
> 把「读 .env」做成应用自身的能力后，三种启动方式都能用；
> 脚本保留给「想用真环境变量」的场景（CI/生产）。

## 1.1 ★ 改了 `jeecg-boot-base-core` 之后必须先 install

`DotEnvEnvironmentPostProcessor` 放在 **`jeecg-boot-base-core`** 模块里。
这个模块被 `jeecg-module-land` 等模块以**独立构件**方式依赖，
Maven 会优先用**本机仓库（`.m2`）里的 jar**，而不是工作区里的 `target/classes`。

所以改过 base-core 之后，若不做下面这步，就会出现
「源码明明改了、运行时却还是旧的」——本次就踩过：
测试报 `ClassNotFoundException: org.jeecg.config.DotEnvEnvironmentPostProcessor`。

```powershell
cd server
mvn -o -pl jeecg-boot-base-core install -DskipTests
```

判断方法 —— 看 `.m2` 里的 jar 时间戳和内容：

```powershell
# jar 里应该能看到这两个条目
jar tf "$env:USERPROFILE\.m2\repository\org\jeecgframework\boot\jeecg-boot-base-core\3.4.3\jeecg-boot-base-core-3.4.3.jar" |
    Select-String "DotEnv|spring.factories"
```

汇编构建（`mvn -pl ... -am`）或先 `mvn install` 整个 `server` 都能避免这个问题。

## 2. 有哪些变量

| 变量 | 用途 | 缺省行为 |
|---|---|---|
| `TJ_DB_HOST` / `TJ_DB_PORT` / `TJ_DB_NAME` | 业务库（也是中台镜像库所在实例） | 无默认值，缺失即启动失败 |
| `TJ_DB_USER` | 数据库账号 | 无默认值 |
| `TJ_DB_PASSWORD` | 数据库口令 | **无默认值**，缺失即报错（见下） |
| `TJ_REDIS_HOST` / `TJ_REDIS_PORT` | Redis | 各 profile 保留自己的原值为默认值 |
| `TJ_REDIS_PASSWORD` | Redis 口令 | 空字符串（本机无口令） |
| `TJ_DRUID_LOGIN_USERNAME` / `TJ_DRUID_LOGIN_PASSWORD` | Druid 监控台 `/druid` | 无默认值 |
| `TJ_ZK_USERNAME` / `TJ_ZK_PASSWORD` | 中台对接专用账号 | 无默认值 |
| `TJ_SIGNATURE_SECRET` | jeecg 签名密钥（前后端一致） | 无默认值 |
| `TJ_KNIFE4J_USERNAME` / `TJ_KNIFE4J_PASSWORD` | Knife4j 文档页 Basic | 无默认值（该功能 `enable: false`） |
| `TJ_MAIL_USERNAME` / `TJ_MAIL_PASSWORD` | 邮件 | 空 |
| `TJ_OSS_ACCESS_KEY` / `TJ_OSS_SECRET_KEY` | 阿里云 OSS | 空 |
| `TJ_MINIO_NAME` / `TJ_MINIO_PASSWORD` | MinIO | 空 |

> 变量名统一加 `TJ_` 前缀，避免与主机上已有的同名环境变量（尤其是 `PASSWORD` 这类）冲突。

## 3. 设计取舍（为什么这么做）

### 3.1 口令一律不设「兜底默认值」

yml 里写的是 `${TJ_DB_PASSWORD}`，**不写** `${TJ_DB_PASSWORD:某个默认口令}`。

理由：默认值只能来自仓库，而「仓库里的口令」正是这次要消灭的东西。
不设默认值的结果是**缺失时启动直接失败**——这是刻意的：

- 失败会告诉你「缺口令」，排查成本几乎为零；
- 而如果给个默认值，它会在开发机上「碰巧能跑」，到了线上才暴露，
  或者更糟：拿错误口令连上了一个不该连的库。

### 3.2 集成测试自己读 `.env`，不用 Maven 插件注入

`LandTestConfig` 在类初始化时读取 `server/.env`，读取顺序是
**系统属性 → 真环境变量 → `.env` → 代码默认值**。

为什么不用 surefire 的 `<environmentVariables>`：
它没有「文件不存在就跳过」的写法。一旦写成
`<TJ_DB_PASSWORD>${env.TJ_DB_PASSWORD}</TJ_DB_PASSWORD>`，
在**没有 `.env` 的 CI 环境**里会因为解析不到 `env.TJ_DB_PASSWORD` 而直接把构建搞挂。
引入 dotenv 插件则要下载新依赖——本工程的依赖是离线锁定的（`.m2` 里有什么才能用什么）。

自己读一个文本文件：零新依赖、IDE 单测与 Maven 两条路都生效、
口令不出现在命令行参数里（也就不会进构建日志或进程列表）。

### 3.2 `.env` 在两处被读取，各自独立

| 读取方 | 生效场景 | 机制 |
|---|---|---|
| `DotEnvEnvironmentPostProcessor`（在 `jeecg-boot-base-core`） | **应用启动**：IDE / `java -jar` / `mvn spring-boot:run` | 在「环境准备阶段」把 `.env` 追加为**最低优先级**的 PropertySource |
| `LandTestConfig`（在 `jeecg-module-land/src/test`） | **集成测试** | 类初始化时自己读文件，写入查找顺序：**系统属性 → 真环境变量 → `.env` → 代码默认值** |

两处都不依赖任何 Maven 插件或新增依赖，原因：

- surefire 的 `<environmentVariables>` 没有「文件不存在就跳过」的写法。一旦写成
  `<TJ_DB_PASSWORD>${env.TJ_DB_PASSWORD}</TJ_DB_PASSWORD>`，
  在**没有 `.env` 的 CI 环境**里会因为解析不到 `env.TJ_DB_PASSWORD` 而直接把构建搞挂。
- 引入 dotenv 插件则要下载新依赖——本工程的依赖是离线锁定的（`.m2` 里有什么才能用什么）。

自己读一个文本文件：零新依赖、IDE 与 Maven 两条路都生效、
口令不出现在命令行参数里（也就不会进构建日志或进程列表）。

### 3.2.1 为什么不用 `spring.config.import`

`spring.config.import` 支持 `optional:file:.env[.properties]`，看似更省事，但
`.env` 的语法并不是 properties 语法——properties 会把 `:` 当键值分隔符，
口令里一旦出现 `:` 就会被**静默截断**，然后报一个「Access denied」
而肉眼看口令完全正确。自己解析可以严格按 `.env` 的习惯来
（忽略 `#` 注释、按第一个 `=` 切分、不剥引号、不去转义）。

### 3.3 `.env` 的解析只做「按第一个 `=` 切分」

没有用 `.NET Properties` 或任何通用 properties 解析器，因为那些解析器会把
`:` `=` `\` 当分隔符/转义符，而口令里出现 `:` 就会**被静默截断**——
截断后的口令连不上库，报的还是「Access denied」，非常难查。

只做三件事：按第一个 `=` 切分、去掉行尾的 `\r`（Windows 编辑过的文件常见）、
去掉可能存在的 UTF-8 BOM（否则第一个键名会带上 BOM 而永远匹配不上）。
值本身不加引号、不写行尾注释，因此也不需要对引号做处理。

### 3.4 Redis 空口令保留引号

yml 里是 `password: '${TJ_REDIS_PASSWORD:}'`（带单引号）。
因为 YAML 里裸的 `password:` 是 `null`、`password: ''` 是空字符串。
原本就是空串，就继续写成空串——**改动越小越安全**。

### 3.5 各 profile 的 Redis 地址保留各自的原值为默认值

`application-test.yml` 的 Redis 是内网 `192.168.1.199`，而 dev/prod 是 `127.0.0.1`。
所以默认值取**该文件原本的取值**，而不是统一写 `127.0.0.1`——
否则「改个默认值就把 test 环境悄悄指向本机」这类问题极难发现。

## 4. 排查手册

| 现象 | 原因 | 处理 |
|---|---|---|
| 启动报 `Could not resolve placeholder 'TJ_DB_HOST'` | 缺 `.env`；或 `jeecg-boot-base-core` 用的是 `.m2` 里的**旧 jar**（不含 `DotEnvEnvironmentPostProcessor`） | 建 `.env`；并执行 `mvn -o -pl jeecg-boot-base-core install -DskipTests`（见 §1.1） |
| 启动日志里没有 `[jeecg] 已加载环境变量文件：…` | 同上；或 `.env` 不在「工作目录及其上 4 级」内 | 用 `-Djeecg.dotenv.location=绝对路径` 显式指定 |
| 测试报 `ClassNotFoundException: org.jeecg.config.DotEnvEnvironmentPostProcessor` | base-core 的 `.m2` jar 是旧的 | 同上，install base-core |
| 启动日志有 `已加载环境变量文件` 但仍解析不了某个键 | 该键在 `.env` 里拼写不同，或行首有空格 | 对照 `.env.example` 的键名 |
| 测试报 `集成测试缺少数据库口令` | 同上（测试链路的提示） | 建 `.env`，或在 IDE 里加 `-Dledger.test.password=...` |
| 报 `Access denied ... (using password: YES)` 但口令看着没错 | 口令被截断（值里含 `:` 且用了通用解析器），或口令在库侧已被改 | 检查 `.env` 里该行是否有未加引号却带 `:` 的值；确认库侧口令 |
| 改了 `TJ_DB_PASSWORD` 但测试仍用旧值 | 系统属性/环境变量优先级高于 `.env` | 检查是否有 `-Dledger.test.password` 或系统级同名环境变量 |
| 测试日志里的口令指纹与 `.env` 不一致 | 同上 | `LandTestConfig` 会打印「长度 + 指纹」，不会打印口令本身，用它对账 |
